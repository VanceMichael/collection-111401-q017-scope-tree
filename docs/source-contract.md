# 门店门户

`/portal` 提供正常浏览器操作。根节点仅包含区域，区域按两条一页懒加载。门店 id 在调区后不变；名称并非身份。父级勾选是动态继承选择，包含未来新增成员；叶子勾选仅代表该门店。视觉上的子项未打勾不表示父级继承失效，“核对范围”展示服务实际采用的集合。

默认业务范围在 fixtures/request.json：只领取 A、C 两个直营网点，不包括加盟门店。必须通过页面交互设置与核对范围；资料交给现有 Archive。可正常读取页面展示和下载结果，不使用控制面代替选择操作。generation=2 将 C 调到东区并新增 D，因此第一次观察树不保证后续范围没有变化。

本地业务 API 是页面自身的数据服务，`/export` 的返回集合才是此次资料对应范围。来源没有自动按“直营”过滤的隐藏选项。

## 浏览器领取流程约束

`src/collector.mjs` 实现的领取流程遵守以下规则：

1. 只通过页面正常交互改变选择：点击复选框、“展开区域”“更多门店”“清空选择”“核对范围”“领取资料”。不直接调用 `/selection`、`/_control` 改写状态，也不使用页面外请求代替按钮操作；测试中的 `/_control` 仅用于演练目录变化。
2. 不依赖父节点勾选：父级继承是动态选择，会把加盟店与未来新增门店带入范围。流程先清空既有选择，再按请求清单逐店勾选叶子，并断言没有任何 `data-inherit` 框处于勾选。
3. 懒加载与分页：每个区域都展开并持续点击“更多门店”直到按钮消失，再用页面上实际枚举到的门店与请求清单核对；清单中的门店缺失、重复或页面标注类型不符（如请求直营却指向加盟门店）时抛出 `ScopeDiscrepancyError`，差异明细包含观察到的完整目录，不猜测缺失节点。
4. 调区处理：记录加载时的 `generation`，在“核对范围”和导出返回处再次比对；版本变化即整页重开、重新核对（默认最多 3 次），持续不稳定则停止且不留收件。门店 id 跨调区稳定，名称不作为身份。
5. 最终生效范围以服务端返回为准：核对 `#scope` 实际门店集合与导出 JSON 的 `ids`、`rows` 都与请求清单完全一致后，才把导出内容交给 `Archive` 并生成回执；否则停止，不保存。

## 本地演练控制

`GET /_health` 返回服务健康状态；`GET /_audit` 仅返回请求路径、方法和体积，不记录凭据。`POST /_control` 接收 JSON，可调整 generation、mode、clock。控制端点只服务于本地演练，不是资料接口，也不是浏览器业务操作入口。每次重新启动服务都会恢复初始数据；生产接入时不部署此控制面。
